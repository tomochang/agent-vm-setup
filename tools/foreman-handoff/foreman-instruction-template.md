# Foreman 指示テンプレ（the resident agent → Foreman、冒頭に「F:」）

今夜の教訓を型にしたもの。指示はこの形で書く。型自体も小さく保つ。

## 1. 件名と目的（1–2行）
- 何を・なぜやるか
- 完了の定義を1行で（何が動けば終わりか）

## 2. スコープ
- やること: 規則単位で1つだけ
- やらないこと: 明示する。**束ね禁止**（2つ以上の部品を1指示・1PRにしない）

## 3. 設計（コードの前に出し切る）
- SPEC の冒頭に**リスク表**（失敗モード／迂回経路／誤用／環境ハザード × 潰し方と検知法）
- 実装前に **Codex が独立にリスクを列挙**し、SPEC と突き合わせる。漏れはコードを書く前に SPEC を直す
- **設計レビューは文書のみで最大3周**（差分と未解決分だけ）。新しい P1 級の設計漏れが出なくなった周で収束。3周で収束しなければ実装に入らず the resident agent に上げる
- 設計原則: **状態を持つな、事実から数えろ** ／ **小さく作って動かす → 少しだけ抽象化 → まだ動くか確認**（records repo 絶対ルール0）

## 4. 予算と停止条件
- 上限 X units（ハード）。**70% で消費＋残見込みを報告**
- 上限到達で、状態にかかわらず停止して報告。例外（起動済みのゲート等）は明示して確認を取る
- 消費は**実測**で報告する。エージェントのライブ値は「未照合」と明記

## 5. 実施の規律
- 実装レビューは**1回集約＋2回目は差分のみ**。2回目で新しい P1 が出たら、直さず the resident agent に上げる
- ゲートは ready の時点でフルセット1回。keep-gates（送信・削除・支払い・main 反映）は維持
- 作業は worktree＋安全 push（plain push 禁止）

## 6. 報告フォーマット
- 結果（PR リンク／マージ可否）
- 実測消費（上限比つき）
- P1/P2 件数（設計／実装／ゲートの別）
- 未検証の項目を明示
- 残件

## 7. 判断が要るとき（Foreman → the resident agent の上げ方）
- 選択肢 A/B＋**推奨を明記**、各案のコスト見積もり、現在の消費実測
- 推奨理由は短く

---
自分（the resident agent）の作業にも同じ型を適用する: 小さく作って動かし、動くものを先に出す。
