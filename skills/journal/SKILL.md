# Journal — 全環境共通の手順

## 入口とモード

正本repositoryは `the records repo`。Web・mobileはGitHub接続で、Codexは対象checkoutまたは同じ接続で読む。別repositoryに作らない。

最初に `CHATGPT.md` → `private/journal/README.md` → `docs/agent-rules/journal.md` と対象日のentry/runを読む。初回例は `private/journal/entries/2026/09/2026-09-17.md`。同じ対話の続きで取得済み内容が十分なら、毎返答で全repoや全情報源を読み直さない。保存の直前は最新版とSHAを再取得する。

- `日記` / `$journal` / `/journal`：prepare。今日の下書きから始める。
- `日記 YYYY-MM-DD`：指定日。日記の対象日と記録日時は別。
- `日記の続き`：continue。最新の未完了runと本人発言原文から再開し、既に答えたことを聞き直さない。
- `保存して`：save。本文と原資料、索引、必要な連動、commit、remote検証まで。
- `月次振り返り YYYY-MM`：review。全対象本文から振り返る。
- `日記の状態`：status。保存・添付転送・実行・通知・認証を分けて報告。
- scheduled：`private/journal/config.json` と `OPERATIONS.md` に従う日次起動。

## 対話契約（prepare / continue より優先）

1. **本人が話し終わるまで割り込まない。** 音声・逐次入力で文が続いている、言いかけ、接続詞で終わる、本人が「まだ続ける」と示している場合は、相づち・質問・解釈・要約を返さない。明確に話が終わったか、本人が応答を求めた時だけ返す。
2. **口調・呼称の訂正は即時適用する。** 「丁寧語で」「ため口を使わない」等はAI自身への指示として扱い、第三者の話へ読み替えない。指摘後に自己弁護・意図説明・指示の復唱で返さず、次の返答から直す。
3. **本人が言っていない意味を先回りで補わない。** 特に話の途中で原因・評価・因果を推測しない。分からない部分は未定義のまま保持する。
4. **質問前に既回答チェックをする。** 現在の会話、対象日のstatements、runのanswered/notesを見て、質問文への答えが既に本人の言葉で存在するなら聞かない。既回答を別表現で確認し直すのも重複質問とする。
5. **一問だけ、目的がある時だけ聞く。** その問いで新しい情報が増えることを内部で一文にできないなら聞かない。本人が質問の意図を尋ねたら意図を説明し、同じ問いをそのまま繰り返さない。
6. **一つの場面を掘る標準は2〜3往復で終了する。** 出来事、本人の感情/感覚の表現、重要な理由・対比・未定義点のうち必要なものが揃ったら、追加の細分化よりdraftへ進む。4問目以降を同じ場面で続けるのは、本人が明示的に深掘りを望む場合だけ。
7. **ゴールを見失わせない。** 2問以上の追加質問が必要と判断した時だけ、「あと1〜2点を確認したらdraftにする」程度に終了条件を短く示す。質問を無期限に連鎖させない。

## prepare → continue

1. 現在の日時・タイムゾーンと対象日を確定。手動指定を優先。深夜は前夜の続きとして扱い、勝手に別日へ分断しない。
2. **コードが走る環境（Mac上のClaude Code / Codex）では、まず `python3 skills/journal/scripts/journal_collect.py --day <対象日>` を実行し、その1日分JSONを一次資料にする**（2026-10-14 本人合意）。Calendar・Gmail（staging除外・送受信区別・PROMOTIONSは件数のみ）・GitHub（全branchのcommitと他repoのpush）・Beeper・期限切れTodoをまとめて取得する。`status` が `ok` 以外の情報源だけ下記の手順で個別に取り直し、取れなかった理由をsourcesに残す。Beeperは**その日に1通でもメッセージがあるチャット全部**（グループ・WhatsApp・アーカイブ・本人が送っていないチャットを含む）を対象にする（2026-10-27 本人指示。10/14の「1対1・本人送信・WhatsApp除外」で石神さんのキャンセル等が落ちた）。恋愛の内容を日記に書くかは、読んだ後で場面ごとに本人が決める。GitHubは records repo に加え、`config.json` の `sources.github.local_repo_roots`（`~/factory`・`~/research`）直下の remote の無いリポも集める。Beeper Desktopが起動していない・Web/mobile環境では `unavailable` になり、チャットなしで進める（欠測として扱い、本人に取得を求めない）。チャット本文はrepoへ丸ごと保存せず、日記に使った部分だけを `source-log.md` に引用する。commitは `areas`（触ったフォルダ）と件名だけなので、日記に関係しそうなものは `git show` で中身を読む。コードが走らない環境では以下の手順で取得する。
   Calendarの予定・場所・変更、Gmailの送受信と利用/注文/手続き記録、GitHubの関連日次ログ・commitを実取得。Calendar・Gmailは `operator@example.com` のみ。`operator-secondary@example.com` は対象外（2026-09-27本人指示）で、取得も「未認証・欠測」の報告も再認証の提案もしない。GitHubはmainだけでなく全branch（`git log --all`）と `gh api users/<github-username>/events` で他repoも確認し、commitは件名だけでなく成果物の中身まで読む（2026-09-27 本人指摘）。ページが残る場合は読む。Calendarがあるだけで実施済み、受信だけで読了/対応済み、保存日時を活動日時とはしない。 対象日のCalendar予定は、entry本文で **実施 / 未実施 / 不明** のいずれかを明示する。「予定があった」「予定が入っていた」のように判定を避けた表現で本文に残さない。不明なら質問で確定させ、確定できなければ「実施は未確認」と書く。支払い時刻から滞在全体を推定しない。
3. **最初の提示は `journal_collect.py --day <対象日> --digest` の出力をそのまま全行見せる**（2026-10-27 本人「要約で必ず落とさない仕組みを作って」）。digestはCalendar・Gmail・GitHub（clawdと手元のリポを話題ごとに件数・時刻つき）・Beeperの全チャット・期限切れTodoを機械的に全件並べる。LLMが項目を選んで3〜5行に縮めない（10/27に、件数最多のkakugo・CI作業・factoryを要約で落とした）。LLMが足してよいのは、digestの後に「読んで分かったこと」を数行と一問だけ。`ok`以外の情報源はdigestに状態が出るので、そのまま見せて理由を添える。取得ID・範囲・時刻・状態をsourcesに残す。保存する本文・原資料の情報量は絞らない。通知や重複の件数を本人の活動量にしない。
4. その日の具体的な場面について一問。本人の自然な表現を先に聞く。記録のない出来事も受け止める。本人発言は原文で保存。白紙から出来事を再入力させない。
5. 本人の語が曖昧なとき、または本人自身が「解像度が低い」と示したときは、**原因の深掘りより先に**辞書を実参照し近い言葉を最大3つ、その違いを短く示す。`private/journal/lexicon.md`は用例・出典への入口。公開項目だけで語義を引用したと称しない。辞書本文が取得できなければAIの候補説明と明記。既に明確な語を無理に言い換えない。本人が選択・修正・併存・保留できるようにする。
6. 必要時だけ、事実/感情/解釈/実際の反応を分け、べき思考・永続化・広汎化・過度な自己責任を点検する。感情を誤りとせず、相手の問題を本人の認知に押しつけない。
7. 対処は必要なら一つ。保留・休む・うれしかった経験を繰り返すも含む。「できたこと/学んだこと」は記録から根拠のある候補を拾う。疲れた日は一言でも終了。時間目安を理由に情報を落とさない。
8. **野生を自動的な改善対象にしない。** 衝動、怒り、逸脱、過集中、寄り道、勝ちへの執着が現れた時は、効率・安定・穏やかさをそれ自体の目的にせず、まず「武器 / 害 / まだ分からない」に分ける。武器または未判定の可能性がある特性には抑制案を先に出さない。変える場合も、人格・欲求全体ではなく期待値の低い暴発に対する局所的な行動ルールを優先する。
9. **外食・会食の評価をSSoTへ同期する。** 当日に実際に訪問した飲食店が会話・Calendar・Gmail等から確認できた場合、本人がまだ評価していなければ、その場面の掘り下げ終了時に一度だけ `◎ / ○ / △ / ×` と理由を短く尋ねる。既に評価・理由が本人の発言にあれば聞き直さない。確定した訪問日・店名・ジャンル・エリア・同行者・評価・メモを `private/operator-restaurant-notes.md` に同期する。店選びの分析や感情の全文は移さず、日記本文とレストランDBの責任を分ける。
10. **対象日までのTodo予定を消し込む。** `python3 skills/journal/scripts/journal_tool.py todo-overdue --day <対象日>` で `private/todo.md` の「今後の確定予定と残作業」から終了日が対象日以前の行（当日分を含む）を列挙する（コードが走らない環境では同表の日付を目視で照合）。各行を、対象日までのentry/statements・Calendar・Gmailの記録から **実施 / 未実施 / 不明** に分ける。Calendarに残っているだけ、日付が過ぎただけでは実施にしない。本人が既に発言していれば聞き直さず、不明な行だけをまとめて一問で確認する（行ごとに別の問いにしない）。
11. **draftは対話の途中で毎回答えごとに書き直さない。** 原文は安全なチェックポイント（標準2〜3往復、話題転換前、終了/保存指示時）でstatements/runへ保持し、entry本文は場面の掘り下げが終わった時にまとめて組み立てる。
12. 全文を返す。各場面の具体情報、否定、条件、本人が分けた論点、未定義箇所を維持。本人の承認・訂正を反映してsave。本人の言葉選びを支えるが、最後の一文の自作を必須課題にしない。

## Gmail取得のアカウント・除外ゲート（manual / scheduled共通）

`private/journal/config.json` の `sources.gmail` を正とし、prepare / continue / scheduled / 障害復旧の再取得すべてに適用する。

1. **検索前にprovider/sessionを確定する。** Gmail connectorではその接続のprofile（`get_profile`等）のemailを実取得し、`operator@example.com` と一致する接続だけを使う。CLIでは `--account operator@example.com` を明示し、同じsessionのprovider profileでも照合する。`to:` / `deliveredto:` の検索条件やブラウザURLだけをアカウント確認の代わりにしない。profile未確認・不一致・確認不能ならGmail取得を `source_failed` として停止し、別アカウントへfallbackしない。接続を切り替えたら再確認する。
2. **OPERATOR-COMPANY staging起因メールだけ除外する。** Fromのメールアドレスdomainが `staging.operator-company.example` またはそのサブドメインなら対象外。2026-09-30に確認した実例は `support@staging.operator-company.example`、件名は `【staging】[OPERATOR-COMPANY]`。件名のOPERATOR-COMPANY/stagingという単語だけ、宛先、本文内の言及だけでは除外しない。通常の `operator-company.example` 発や、法律・金融を含む実際の個人宛連絡は残す。未確認の別domainを推測で追加しない。
3. **message単位で、保存より先に除外する。** 検索結果・ページング・thread内の各message・再取得にも同じ判定を適用し、除外メールをsource-log / entry / 日記通知候補へ入れない。Gmailの削除・archive・label変更はしない。Fromが欠落・曖昧ならmetadataを確認し、確認できなければ当該取得を未完了として扱う。
4. Python実行可能なら `skills/journal/scripts/gmail_source_policy.py` を使う。取得したprovider profileのJSONを `--profile` に渡して検索前に検査し、取得後は同じprofileとmessage配列JSONを `--messages` に渡して、成功した出力だけを原資料へ採用する。一時JSONは `.journal-runtime/` に置きcommitしない。PythonがないWeb環境では1〜3を同じ順序で実施する。このhelperはネットワークcollectorや認証hookではなく、渡されたprofileの出所を検証できないため、provider実取得の代わりに自己申告JSONを作らない。
5. sourcesには確認したaccount・取得時刻・範囲・適用した除外ルール・除外件数だけを運用記録として残す。除外本文を保存しない。既存のdurable保存確認・claim前ゲート・安全拒否時の停止条件は引き続き適用する。

## save（省略不可）

### 原資料と本文の役割分担

- `statements.md` は**逐語原資料**。本人発言をそのまま保存し、必要なAI質問だけを文脈として区別して添える。本人発言ごとにAIの解釈・要約・「Txxで明らかになったこと」を追記しない。それらはrunの運用メモか、最終entryの構成にのみ使う。
- `entries/...` は**読み返す本文**。逐語ログの複製ではない。distinctな事実・条件・否定・比較・因果・未定義を一度ずつ書く。
- **一つの意味は一度だけ。** 「引用→同義の言い換え」「要点の列挙→直後に同じ内容を文章で再説明」「見出し直下の要約→本文で再要約」をしない。引用は、言い換えるとニュアンスが落ちる本人固有の表現に限る。引用した場合、その直後の文章は新しい情報を足す時だけ書く。
- 情報保持と冗長化を区別する。情報量を守るとは、条件・否定・対比・対象・因果を残すことであり、同じ意味を複数回書くことではない。
- Calendar/Gmail/GitHubの記録のうち、**後からその日の生活・行動を復元する具体情報**（実利用・注文・決済、移動/訪問の裏付け、本人が行った調査・作業等）はentryの「今日の記録」等へ残す。金額・店名・時刻・未特定状態も、確認できた粒度のまま保持する。単に届いただけの請求案内・キャンペーン・通知や、日記理解に寄与しない運用ログは本文へ入れない。完全な取得範囲・message/event ID・検索条件・未確認事項は`source-log.md`へ置く。
- AIの作業過程・保存失敗・スキル運用批評は、**それ自体が本人にとってその日の出来事・反省である場合だけ**本文へ入れる。特に、本人が日記を読み返して欠陥を発見し、そのフィードバックでjournal skillや生活システム自体を改善した場合は、単なる運用ログではなくその日の活動・学習として本文へ残す。commit番号や機械的な変更一覧はrun/OPERATIONS/Git履歴へ分離する。それ以外はrun/source-logへ。

### draft品質ゲート

本人にdraftを見せる前に、sourceとdraftを照合して次を確認する。

1. **Coverage:** distinctな本人情報（事実、数値、否定、条件、対比、比喩、未定義）が落ちていない。
2. **Day reconstruction:** evidenceとentryを突合し、当日の生活・行動を後から復元する具体情報（実利用・注文・決済、確認できた移動/訪問、本人が行った調査・作業）が、単なる「補助記録」という理由でentryから脱落していない。逆に受信しただけの請求案内・広告・一般通知は水増ししない。
3. **Non-redundancy:** 各意味が原則1回だけ現れる。引用の直後に同義説明がない。
4. **Attribution:** AIが作った原因・感情・評価を本人のものとして書いていない。
5. **Question debt:** 本人が既に答えた問いや、回答不要とした問いを未解決扱いしていない。
6. **Restaurant sync:** 当日の実訪問飲食店が確認できる場合、各店について `private/operator-restaurant-notes.md` の既存評価または当日会話の本人評価を照合する。未評価の実訪問店が残っていれば、draft確定前に一度だけ `◎ / ○ / △ / ×` と理由を尋ねる。評価取得後はentryとレストランSSoTの両方へ同期する。デリバリー/テイクアウトは「訪問」と推測しない。
7. **Todo reconciliation:** 対象日以前の日付（当日を含む）で「今後の確定予定と残作業」に残る行がゼロか、各行が実施/未実施/不明のいずれかに判定済み。実施はsave時に日付・根拠付きで `private/todo_done.md` へ移し、未実施は理由付きで残し、不明は行末に `【要確認】` と確認日を付けて残す。判定なしに削除しない。entry本文に当日予定を「予定があった」とだけ書いた箇所があれば、このゲートは通らない（2026-09-25 銀行面談の再発防止）。
8. **Upcoming schedule consistency:** 未来の予定も `docs/agent-rules/relationship-sync.md` の状態・配置先・根拠の整合を確認する。確定済み予定を仮の欄に、完了済みの連絡・手配を残作業に残さない。部分完了は未完了部分を保持し、手配完了を予定の実施済みへ拡張しない。実行環境で可能なら `python3 scripts/todo_consistency.py check --root .` を実行し、タグ付き範囲・既知パターンの結果と未検査coverageを区別する。
9. **Stop condition:** 追加質問なしで読めるならdraftを返す。完全性のためだけの追加質問をしない。

- `sources/YYYY/MM/day/statements.md`：本人発言と訂正を原文で、順序・発言主体を明確に保存。質問の文脈が必要ならAIの質問を区別して添える。
- `source-log.md`：必要な本文、記録ID、日時、出典種別、確認範囲。秘密・認証URLは除外。2026-09-27以前の既存日記ではlegacy名 `evidence.md` も有効な原資料として読み続け、改名目的だけで過去ファイルを変更しない。
- **Web/automationから新規原資料を作るときは `evidence.md` を作らない。** 2026-09-30の実測でGitHub connectorは同一ディレクトリ・同内容でも新規 `evidence.md` のcreateだけをsafety checkで拒否し、`source-log.md` は成功した。既存 `evidence.md` のupdateは成功したため、内容やprivate pathではなくcreate時のfilenameに依存するconnector側false positiveと判断する。
- 添付は実ファイル、元名、SHA-256、転送先、転送状態を記録。原本の未転送を隠さない。
- 正本は `entries/YYYY/MM/day.md`。`TEMPLATE.md`の最小メタデータ、本文、固定アンカーと相対リンク。短い教訓だけに置き換えない。
- draftとconfirmedを区別。2026-09-18に日記・原資料の通常保存は承認済み。毎回保存許可を取り直さず実行するが、本人が確認していない生成本文をconfirmedにしない。
- 本人が表示中のdraftに「OK」「これでよい」等で明示確認したら、その**表示した本文そのもの**をconfirmedにする。確認後に内容を足したり再要約したりしない。許される変更はstatus・確認注記・保護hash・索引/run等の保存メタデータのみ。
- 承認済み本文は自動再要約禁止。本人の明示訂正/追加承認のある変更だけ、原文・変更理由・保護ハッシュを同時更新。後日の認識の変化は別日の本文へ。
- 年次索引・感情用例・必要なテーマリンクを更新。ただし `indexes/`・`lexicon.md`・`topics/` は**検索入口**であり、entry本文の再要約層にしない。短い用例・区別・リンクだけで足りるならそれ以上書かない。人物/接触/Todoは `docs/agent-rules/relationship-sync.md` を適用。未特定PIDを推測しない、新規人物を無承認作成しない。未解決事項はrun/OPERATIONSへ。
- 実行環境で可能なら `python3 skills/journal/scripts/journal_tool.py validate` とテスト。Webでコードが走らなければ同じチェックを原文/差分/ハッシュで行う。検査していないのにPASSと言わない。
- **CoachEd宿題期間（2026-10-01〜10-07）の追加完了条件:** 確定日記から当日1場面を既存の共有ワークシートへ反映する。本人が述べていない体感・感情は捏造せず「未記録」とする。書込み後にGoogle Slidesの対象スライドを新しく取得し、題名と4欄の完全一致を確認して `private/journal/worksheet-sync-tests/journal_YYYYMMDD.json` にentry SHA-256・対象slide ID・payload・readback revisionと時刻を記録する。`python3 skills/journal/scripts/journal_tool.py worksheet-gate --date YYYY-MM-DD` がerrorsなしになるまで、日記と宿題をまとめて「完了」と報告しない。接続不能なら「日記保存済み／ワークシート未反映」と明示する。
- 通常記録は `CHATGPT.md` の「書き込みルール」に従い、承認済み保存のmain反映を聞き直さず、remote default branchへの反映・再読確認まで完了させる。branchだけの保存は統合担当と次の操作を記録した未完了とする。実行ルール・コードは別branch→検証→PR・review。直前SHA確認、競合時再取得・統合、force push禁止。ローカルの未関連変更を巻き込まず、platform/toolの権限・確認を上書きしない。
- 保存後はremote mainの実ファイル/commitを再読し、本文・原資料・関連リンクを確認。成功時だけcommitと要点を返す。保存失敗時は未完了のまま原文を保持。

## scheduled（本人が毎日実行を依頼済み）

初期設定はJST23時台〜翌3時台に1時間間隔で機会を確認、未実行時は翌11時に回復。各対象日に問いは最大1回。設定は本人指定の時刻ではなく、この対話に基づく初期運用値。

1. **entryを最優先で確認する。** 対象日のentryが存在し `status: confirmed` なら、それを権威ある停止条件として新しい問い・source再収集・claimを一切行わない。runがawaiting_user / entry=null等で矛盾していても、confirmed entryを上書き・再質問せず、runをconfirmedへ自己修復し索引漏れがあれば補う。entryが未確認/不存在の場合に限りrunを見て、manual_session、awaiting_user、通知sent/claimed/delivery_uncertainなら新しい問いを送らない。
2. まだならCalendarで会食・面会・移動中と終了後30分を確認し、次回へ延期。終日旅程の存在だけで永久に延期しない。Calendarを読めなければ空いていると推定しない。
3. 準備可能時のみ残る情報源を取得。新規原資料の保存先は実行開始時から `source-log.md` とする。connector safety checkが拒否した場合はその実行を停止し、別名・別tool・別経路へ切り替えて同じ書込みを再試行しない。拒否理由を取得できた範囲で記録し、承認または権限の問題が解消したことを確認するまで当該書込みを自動再試行しない。通常の取得・通信失敗はsourceごとに記録して再試行する。11時にも直らない実行障害だけを1日1回報告する。本人の無返答は障害ではない。
4. **原資料のdurable保存確認をclaimの前提にする。** 対象日の取得範囲・出典ID・必要な内容を保存し、remote mainから再取得して書込み内容との一致を確認できた場合だけ、日付をキーとするrunのclaimをremoteへ条件付き書込みし、重複を防ぐ。保存拒否・再読失敗・内容不一致の場合はclaimも通常の日記通知も行わない。`source_recovered`やファイルの存在だけでは保存完了としない。実行メタデータだけの復旧記録は原資料の代用品にせず、詳細payloadが失われていれば情報源から再取得し、取得時刻と範囲を新たに記録する。送達とGit保存は別システムなので厳密exactly-onceを保証しない。送れたか不明ならdelivery_uncertainにし自動再送せず状態を確認。
5. 3〜5行と一問を届ける。個人情報を通知タイトルへ入れない。本人の回答がない間に感情の捏造、空のconfirmed日記作成、追い通知をしない。
6. 定期実行は起動機会を作る仕組みで、本人の返答やOS通知許可を強制できない。障害/未回答/停止/送達不明を区別して復旧する。

## review

月次振り返りの第一目的は、本人が `private/journal/entries/YYYY/MM/` にある一か月分の日記本文を自分で読み返し、記憶・感情・意味の変化を自分の言葉で捉えること。AIによる分析レポートを先に作らない。エージェント作業ログである `memory/` は月次振り返りの対象へ混ぜない。

1. 原則として対象月の終了後に行う。月の途中なら、本人が明示的に中間振り返りを求めない限り、月次レビューを作らず、まだ対象期間が完了していないと伝える。
2. 対象月の `private/journal/entries/YYYY/MM/` にある日記全文を列挙する。存在しない日は「出来事なし」と扱わず、未記録として示す。Calendar、Gmail、`memory/`、commit履歴を月次本文の代用品にしない。
3. 本人が連続して読める「読み返しパック」を日記本文だけから作る。本文をAI要約へ置き換えず、時系列、正本へのリンク、固定SHA、未記録日を示す。読み返しパックは正本の代替ではなく、レビュー時点の閲覧用スナップショット。
4. 最初に本人へ読み返しパックを渡し、通読してもらう。AIはこの段階でパターン・成長・教訓・翌月の行動を提示しない。
5. 読了後、強く残った箇所、今は見え方が違う箇所、忘れていた箇所、続けたい／やめたいことのうち、本人が自然に選んだ入口から一問ずつ振り返る。回答候補で本人の考えを狭めない。
6. 本人の回答を原文で保持する。AIは言葉の候補、出来事間の対比、見落としの確認を補助できるが、本人より先に因果・価値観・成長物語を確定しない。
7. 十分に振り返った後で、本人の言葉を中心に月次レビュー本文を整理する。AI独自の分析を加える場合は短い仮説として明確に分離し、本人が採用・修正・棄却できるようにする。
8. **野生の損益を分けて見る。** 日記に該当場面がある月は、「合理性を外れた衝動・怒り・寄り道・過集中が価値を生んだ場面」と「期待値の低い暴発として純損失だった場面」を対にして確認する。結論が出ないものは「まだ分からない」のまま残し、野生の総量を減らす目標へ変換しない。
9. 日付・アンカーへリンクし、反例と欠測を扱う。レビューは本人確認前はdraftまたはawaiting_userであり、日記・人格・価値観SSoTへ自動昇格しない。
10. 翌月に試すことは、本人自身の振り返りから出た候補を最大一つ選ぶ。AIが先に行動目標を並べて選択を迫らない。過去本文を削らない。
11. 読み返しパック、対象ファイル、本人発言の原資料、commitを残す。途中なら再開位置、読了状態、既に答えた問いを記録する。
